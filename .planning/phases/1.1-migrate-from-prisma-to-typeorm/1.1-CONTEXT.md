# Phase 1.1: Migrate from prisma to typeorm - Context

**Gathered:** 2026-04-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace Prisma ORM with TypeORM across the entire codebase. Remove PrismaService, PrismaModule, prisma.schema, and generated Prisma client. Install and configure TypeORM with equivalent functionality — the same 2 models (User, Event), working migrations, and a clean module structure that downstream phases can build on.

**In scope:**
- Remove all Prisma dependencies and generated files
- Install `@nestjs/typeorm`, `typeorm`, `pg`
- Define User and Event as decorator-based TypeORM entities
- Create `src/database/data-source.ts` for TypeORM CLI
- Wire `TypeOrmModule.forRootAsync()` in AppModule
- Write a single baseline migration covering the full current schema
- Replace PrismaModule/PrismaService with TypeORM equivalents

**Out of scope:**
- Adding new models or fields (those belong to their respective phases)
- RSVP, Category, Organizer entities (Phase 3–8)
- Any business logic changes

</domain>

<decisions>
## Implementation Decisions

### Entity Definition Style
- **D-01:** Use **decorator-based entities** — `@Entity()`, `@Column()`, `@PrimaryColumn()`, `@CreateDateColumn()`, `@UpdateDateColumn()` on plain TypeScript classes. This supersedes the prior CLAUDE.md rule ("no TypeORM decorators") which was written before the TypeORM migration was decided.
- **D-02:** Entity files live at `src/**/*.entity.ts`. Convention: `user.entity.ts`, `event.entity.ts`.

### Migration Strategy
- **D-03:** **Single baseline migration** — squash the entire current schema (users + events tables with all VarChar constraints, soft-delete column, enum) into one clean TypeORM migration. Existing `prisma/migrations/` history is archived/removed, not carried forward.
- **D-04:** `synchronize: true` is allowed **only when `NODE_ENV === 'development'`** for fast local iteration. It is explicitly `false` in staging and production. Must be documented clearly in code comments to prevent accidental prod enablement.

### Repository Injection Pattern
- **D-05:** Use `TypeOrmModule.forFeature([Entity])` in each feature module and `@InjectRepository(Entity)` in services. NestJS standard — clean module boundaries, testable, consistent with future phases (Users, Events, etc.).

### TypeORM Data Source Configuration
- **D-06:** `AppModule` uses `TypeOrmModule.forRootAsync({ useFactory: (cfg: ConfigService) => ... })` to read `DATABASE_URL` and `NODE_ENV` from ConfigService (already wired in Phase 1).
- **D-07:** A separate `src/database/data-source.ts` exports a `DataSource` instance for the TypeORM CLI (`migration:generate`, `migration:run`, `migration:revert`). It reads `DATABASE_URL` directly from `process.env` (no NestJS bootstrap needed).
- **D-08:** `package.json` gets `typeorm` scripts: `migration:generate`, `migration:run`, `migration:revert` pointing at `src/database/data-source.ts`.

### Claude's Discretion
- Entity file placement (flat in `src/database/entities/` vs co-located with future modules) — Claude may choose the approach that best prepares for downstream phases.
- Whether to keep the `prisma/` directory around with a deprecation note or delete it entirely.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/config/env.validation.ts` — Already validates `DATABASE_URL`; TypeORM config can read from the same validated env
- `ConfigModule` (global) — Available everywhere via `ConfigService`; `forRootAsync` factory injects it without re-importing

### Established Patterns
- `OnModuleInit`/`OnModuleDestroy` lifecycle hooks — Used in PrismaService; TypeORM manages its own connection lifecycle so these are no longer needed in the replacement
- `PrismaPg` adapter pattern — Current setup uses `@prisma/adapter-pg` with a connection string; TypeORM uses `type: 'postgres', url: DATABASE_URL` directly

### Integration Points
- `AppModule` imports `PrismaModule` — this import is replaced by `TypeOrmModule.forRootAsync()`
- No feature modules exist yet that inject `PrismaService` — migration is clean, no ripple effects

</code_context>

<specifics>
## Specific Ideas

- The `forRootAsync` factory should check `NODE_ENV` to toggle `synchronize` — exact pattern confirmed during discussion:
  ```ts
  synchronize: cfg.get('NODE_ENV') === 'development',
  ```
- `data-source.ts` reads from `process.env.DATABASE_URL` directly (not ConfigService) so the TypeORM CLI can run without booting NestJS.
