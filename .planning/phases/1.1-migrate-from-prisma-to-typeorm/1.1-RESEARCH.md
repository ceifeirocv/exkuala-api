## Summary

This phase replaces Prisma with TypeORM across the entire codebase. The scope is purely mechanical: remove all Prisma packages and generated files, install `@nestjs/typeorm` + `typeorm`, replicate the two existing models (User, Event) as decorator-based TypeORM entities, wire `TypeOrmModule.forRootAsync()` in AppModule, and produce a single baseline migration.

The primary technical challenge is the primary key strategy: Prisma provided `@default(cuid())` natively; TypeORM has no built-in CUID support and requires a `@BeforeInsert()` hook with `@paralleldrive/cuid2`. The secondary challenge is the CLI/migration setup — the project uses `"module": "nodenext"` in tsconfig, which causes `"Cannot use import statement outside a module"` errors when TypeORM CLI tries to load TypeScript entity files directly. The solution is a build-first approach: compile to `dist/` first, then run migration commands against the compiled JS.

The existing infrastructure is clean — there are no feature modules that inject `PrismaService`, so the migration has no ripple effects beyond AppModule and the removed prisma/ files.

**Primary recommendation:** Use `typeorm-ts-node-commonjs` for migration scripts where possible; for `migration:generate` on a `nodenext` project, use the build-first pattern pointing data-source.ts entities and migrations at `dist/**` paths.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|

| Repository injection | API / Backend (feature modules) | — | `forFeature` + `@InjectRepository` per module boundary |
| CUID generation | Entity layer (`@BeforeInsert`) | — | TypeORM has no native CUID; hook fires before INSERT |

### Pattern 1: TypeOrmModule.forRootAsync with ConfigService

```typescript
// src/app.module.ts
import { TypeOrmModule } from '@nestjs/typeorm';
import { ConfigService } from '@nestjs/config';
import { UserEntity } from './users/user.entity';
import { EventEntity } from './events/event.entity';

TypeOrmModule.forRootAsync({
  inject: [ConfigService],
  useFactory: (cfg: ConfigService) => ({
    type: 'postgres',
    url: cfg.get<string>('DATABASE_URL'),
    entities: [UserEntity, EventEntity],
    migrations: [__dirname + '/database/migrations/*{.ts,.js}'],
    // IMPORTANT: synchronize only in development — NEVER in production
    synchronize: cfg.get<string>('NODE_ENV') === 'development',
    migrationsRun: false,
    logging: cfg.get<string>('NODE_ENV') === 'development',
  }),
})
```

### Pattern 2: Entity with CUID Primary Key

Prisma provided `@default(cuid())` natively. TypeORM has no built-in CUID support. The standard pattern is `@PrimaryColumn` + `@BeforeInsert()`:

```typescript
// src/users/user.entity.ts
import { createId } from '@paralleldrive/cuid2';
import {
  Entity, PrimaryColumn, Column,
  CreateDateColumn, UpdateDateColumn,
} from 'typeorm';

@Entity('users')
export class UserEntity {
  @PrimaryColumn({ type: 'varchar', length: 30 })
  id: string;

  @Column({ type: 'varchar', length: 128, unique: true })
  auth0Id: string;

  @CreateDateColumn()
  createdAt: Date;

  @UpdateDateColumn()
  updatedAt: Date;

  @BeforeInsert()
  generateId() {
    if (!this.id) {
      this.id = createId();
    }
  }
}
```

[CITED: TypeORM decorator reference + @paralleldrive/cuid2 README] [VERIFIED: npm registry for cuid2 3.3.0]

**Why `if (!this.id)`:** Allows tests to inject a known ID while still auto-generating in production. [ASSUMED — common defensive pattern, not official doc claim]

### Pattern 3: Event Entity with Enum + Soft Delete + Decimal

```typescript
// src/events/event.entity.ts
import { createId } from '@paralleldrive/cuid2';
import {
  Entity, PrimaryColumn, Column,
  CreateDateColumn, UpdateDateColumn, DeleteDateColumn,
  BeforeInsert,
} from 'typeorm';

export enum EventStatus {
  DRAFT = 'DRAFT',
  PUBLISHED = 'PUBLISHED',
  CANCELLED = 'CANCELLED',
}

@Entity('events')
export class EventEntity {
  @PrimaryColumn({ type: 'varchar', length: 30 })
  id: string;

  @Column({ type: 'varchar', length: 200 })
  title: string;

  @Column({ type: 'varchar', length: 5000, nullable: true })
  description: string | null;

  @Column({ type: 'timestamptz' })
  startAt: Date;

  @Column({ type: 'timestamptz', nullable: true })
  endAt: Date | null;

  @Column({ type: 'varchar', length: 200, nullable: true })
  venueName: string | null;

  @Column({ type: 'varchar', length: 500, nullable: true })
  address: string | null;

  @Column({ type: 'varchar', length: 30, nullable: true })
  categoryId: string | null;

  @Column({
    type: 'decimal',
    precision: 10,
    scale: 2,
    nullable: true,
    transformer: {
      to: (v: number | null) => v,
      from: (v: string | null) => (v === null ? null : parseFloat(v)),
    },
  })
  ticketPrice: number | null;

  @Column({ type: 'varchar', length: 2048, nullable: true })
  externalTicketUrl: string | null;

  @Column({
    type: 'enum',
    enum: EventStatus,
    enumName: 'event_status',
    default: EventStatus.DRAFT,
  })
  status: EventStatus;

  @Column({ type: 'varchar', length: 30, nullable: true })
  organizerId: string | null;

  @DeleteDateColumn({ nullable: true })
  deletedAt: Date | null;

  @CreateDateColumn()
  createdAt: Date;

  @UpdateDateColumn()
  updatedAt: Date;

  @BeforeInsert()
  generateId() {
    if (!this.id) {
      this.id = createId();
    }
  }
}
```

### Pattern 4: data-source.ts for CLI

```typescript
// src/database/data-source.ts
import 'dotenv/config'; // load .env before process.env access
import { DataSource } from 'typeorm';

// Note: This file runs WITHOUT NestJS bootstrap (TypeORM CLI only).
// Do NOT import ConfigService here — use process.env directly.
export const AppDataSource = new DataSource({
  type: 'postgres',
  url: process.env.DATABASE_URL,
  entities: ['dist/**/*.entity.js'],
  migrations: ['dist/database/migrations/*.js'],
  synchronize: false,
  logging: false,
});
```

**Why `dist/**` paths:** With `"module": "nodenext"` in tsconfig, running TypeORM CLI against TypeScript source files triggers "Cannot use import statement outside a module". The safe approach is build-first: compile to dist/ then run CLI against compiled JS. [VERIFIED: multiple community reports + official TypeORM docs recommendation]

### Pattern 5: package.json Migration Scripts

```json
{
  "scripts": {
    "migration:generate": "npm run build && npx typeorm migration:generate src/database/migrations/migration -d dist/database/data-source.js",
    "migration:run":      "npm run build && npx typeorm migration:run -d dist/database/data-source.js",
    "migration:revert":   "npm run build && npx typeorm migration:revert -d dist/database/data-source.js"
  }
}
```

**Why build-first:** `"module": "nodenext"` in this project's tsconfig means `typeorm-ts-node-commonjs` and direct ts-node invocations will fail with "Cannot use import statement outside a module". [VERIFIED: github.com/nestjs/nest/issues/15554 + community reports 2024-2025]

**Alternative for migration:generate naming:** Pass a descriptive name: `npm run migration:generate --name=baseline`  — but because the script embeds the path, the planner should use a fixed path like `src/database/migrations/baseline`. Generated file will be `<timestamp>-baseline.ts` in `src/database/migrations/`.

**Important:** After `migration:generate`, the generated file is a `.ts` file in `src/database/migrations/`. After `npm run build`, the dist/ contains the corresponding `.js`. The CLI runs against dist.

### Anti-Patterns to Avoid

- **Using `@PrimaryGeneratedColumn('uuid')`** for cuid-style IDs: generates UUID v4, not cuid. Schema column type is varchar(30) — cuid IDs are ~24 chars, UUIDs are 36 chars. [VERIFIED: cuid2 README]
- **`synchronize: true` without NODE_ENV guard:** Will auto-alter tables in production, silently dropping columns. Always guard with `NODE_ENV === 'development'`. [CITED: TypeORM docs warning]
- **Missing `enumName` on PostgreSQL enum:** Without `enumName: 'event_status'`, TypeORM generates an enum type name from the table+column name combo. If you later add another table using the same enum, TypeORM tries to CREATE TYPE again and the migration fails. Always specify `enumName`. [VERIFIED: github.com/typeorm/typeorm/issues/4106 + issue #9233]
- **Importing from `typeorm/browser`:** IDEs sometimes auto-import from the browser bundle. Always import from `typeorm`. [CITED: community reports]
- **Referencing `.ts` files in data-source.ts entities/migrations arrays:** Breaks with `nodenext` module. Use `dist/**/*.js` paths. [VERIFIED: github.com/nestjs/nest/issues/15554]
- **Forgetting `dotenv/config` import in data-source.ts:** Without it, `process.env.DATABASE_URL` is undefined when CLI runs. [ASSUMED — standard Node.js dotenv pattern]
- **Keeping `postinstall: "prisma generate"` in package.json:** Must be removed after migration; it will fail without the `prisma` package. [ASSUMED — obvious dependency]

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CUID generation | Custom timestamp + random string | `@paralleldrive/cuid2` `createId()` | Collision-resistant, security-audited, produces exactly Prisma-compatible IDs |
| Decimal serialization | Manual string-to-float | TypeORM column transformer | PostgreSQL returns DECIMAL as string; transformer pattern is the idiomatic TypeORM solution |
| Soft delete filtering | Manual `WHERE deletedAt IS NULL` in every query | `@DeleteDateColumn` + `repository.softDelete()` | TypeORM automatically adds `deletedAt IS NULL` to all standard find queries; manual pattern creates drift risk |
| Migration timestamps | Manual naming | TypeORM CLI `migration:generate` | CLI prepends Unix timestamp automatically |
| Connection lifecycle | Manual `connect()` / `disconnect()` | `TypeOrmModule.forRootAsync()` | Module handles pool lifecycle; `OnModuleInit`/`OnModuleDestroy` are no longer needed |

## Common Pitfalls

### Pitfall 1: "Cannot use import statement outside a module" with migration CLI

**What goes wrong:** Running `npx typeorm-ts-node-commonjs migration:generate` against `.ts` entity files in a project with `"module": "nodenext"` produces `SyntaxError: Cannot use import statement outside a module`.
**Why it happens:** `nodenext` module resolution expects ES module syntax, but `typeorm-ts-node-commonjs` forces CommonJS transpilation which conflicts at the Node.js loader level.
**How to avoid:** Use build-first approach — `npm run build && npx typeorm migration:generate ... -d dist/database/data-source.js`. Point `data-source.ts` entities/migrations at `dist/**/*.js` paths.
**Warning signs:** Any import error when running migration scripts; "unexpected token" in ts-node output.

### Pitfall 2: enumName missing causes migration drift

**What goes wrong:** Generated migration has `CREATE TYPE "public"."events_status_enum"` (auto-named). When a second entity uses the same enum without `enumName`, TypeORM tries to CREATE TYPE again, causing migration failure: `type "public"."events_status_enum" already exists`.
**Why it happens:** TypeORM generates enum type names from `<table>_<column>_enum` when `enumName` is absent. If two tables reference the same TS enum without the same `enumName`, TypeORM creates two PG types.
**How to avoid:** Always specify `enumName: 'event_status'` (or chosen name) in the `@Column` options.
**Warning signs:** "already exists" errors in migration:run; duplicate CREATE TYPE statements in generated migration SQL.

### Pitfall 3: Decimal column returned as string

**What goes wrong:** `ticketPrice` comes back as `"10.50"` (string) from the database, not `10.5` (number). This silently breaks arithmetic or comparison logic in services.
**Why it happens:** PostgreSQL DECIMAL/NUMERIC types are serialized as strings by the `pg` driver to avoid floating-point precision loss. TypeORM does NOT auto-coerce.
**How to avoid:** Add a transformer to the `@Column` definition: `transformer: { to: v => v, from: v => v === null ? null : parseFloat(v) }`.
**Warning signs:** Strict TypeScript type errors; values like `"10.50"` in JSON responses; arithmetic producing `NaN`.

### Pitfall 4: @DeleteDateColumn vs nullable DateTime — behavior difference

**What goes wrong:** Using a plain `@Column({ nullable: true }) deletedAt: Date | null` instead of `@DeleteDateColumn()` means TypeORM does NOT automatically filter deleted records. All `find()` calls return soft-deleted rows.
**Why it happens:** TypeORM's automatic soft-delete filtering only activates when the column is decorated with `@DeleteDateColumn`. A plain nullable column is opaque to TypeORM.
**How to avoid:** Use `@DeleteDateColumn()` for `deletedAt`. Use `repository.softDelete(id)` instead of `repository.delete(id)` to perform soft deletes. Use `repository.findOne({ withDeleted: true })` when you need to see deleted records.
**Warning signs:** Deleted records appearing in listings; `softDelete()` not updating the column.

### Pitfall 5: postinstall script still running prisma generate

**What goes wrong:** `npm install` runs `postinstall: "prisma generate"` and fails with "prisma: not found" after Prisma packages are removed.
**Why it happens:** `package.json` still has the postinstall hook from the original setup.
**How to avoid:** Remove `"postinstall": "prisma generate"` from `package.json` scripts in the same PR that removes Prisma packages.
**Warning signs:** `npm install` fails in CI/CD after migration.

### Pitfall 6: Entities listed in AppModule but not in DataSource (and vice versa)

**What goes wrong:** Migration:generate produces an empty or partial migration because `data-source.ts` doesn't include all entities.
**Why it happens:** AppModule's `forRootAsync` and `data-source.ts` are two separate configurations — keeping them in sync is manual.
**How to avoid:** Keep both configs referencing the same set of entities. Strategy: AppModule imports entity classes explicitly; `data-source.ts` uses glob `dist/**/*.entity.js`. The glob approach in data-source.ts is more resilient to additions.
**Warning signs:** `migration:generate` outputs `No changes in database schema were found` when you know there should be changes; or generates extra CREATE TABLE statements for tables that already exist.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `Connection` (TypeORM 0.2) | `DataSource` (TypeORM 0.3) | TypeORM 0.3.0 (2022) | All TypeORM docs/examples pre-0.3 are obsolete; `Connection` and `createConnection` are removed |
| `ormconfig.json` / `ormconfig.ts` (0.2) | Explicit `DataSource` instance in `data-source.ts` | TypeORM 0.3.0 | `ormconfig` auto-discovery is removed; must instantiate DataSource explicitly |
| `typeorm migration:generate` against TS source | `npm run build && typeorm migration:generate` against `dist/` | NestJS nodenext (2023+) | nodenext breaks ts-node-based CLI; build-first is the reliable workaround |
| Prisma `@default(cuid())` | `@BeforeInsert()` + `createId()` from `@paralleldrive/cuid2` | This migration | No native CUID support in TypeORM; must wire manually |

**Deprecated/outdated:**
- `createConnection()`, `getConnection()`, `getRepository()` from TypeORM 0.2 — all removed in 0.3. Any blog post or Stack Overflow answer using these is obsolete.
- `ormconfig.json` auto-discovery — removed in TypeORM 0.3.
- `@nestjs/typeorm` versions below 10 — no longer compatible with NestJS 11.

| A3 | `timestamptz` is the correct PostgreSQL type for DateTime columns | Event entity | Low risk: Prisma maps DateTime to `timestamptz` by default; TypeORM `timestamp` (without tz) is valid but loses timezone — timestamptz is safer |
| A4 | Existing tables in the database match the Prisma schema exactly (no schema drift) | Baseline migration | Medium: if schema drift exists, `migration:generate` will produce incorrect baseline; requires a clean DB or manual baseline writing |
