# Phase 1.1: Code Review Report

**Reviewed:** 2026-04-19T00:00:00Z

## Summary

This review covers the Prisma → TypeORM migration delivered in phase 1.1. The baseline migration SQL, entity definitions, decimal transformer, soft-delete wiring, and CLI data-source are all well-structured. The critical issue is that `synchronize: true` is enabled in the development environment in `app.module.ts`, which directly undermines the migration-first workflow the project has established. Two warnings cover a migrations-path glob that includes `.ts` source files at runtime (fragile), and `PORT` being read from raw `process.env` in `main.ts` rather than through the validated `ConfigService`. Three info items cover a redundant decorator option, missing FK constraints in the baseline migration, and test assertions that are too shallow to catch decorator regressions.

## Critical Issues

### CR-01: `synchronize: true` Enabled in Development Bypasses Migration Discipline

**File:** `src/app.module.ts:26`

**Issue:** `synchronize` is set to `true` when `NODE_ENV === 'development'`. TypeORM's `synchronize` mode auto-applies entity schema changes to the database without generating or running a migration file. This means:

1. A developer who adds, renames, or removes a column from an entity will have their local DB schema silently diverged from what the migration history represents.
2. When that developer runs `migration:generate`, TypeORM diffs the current entity state against the DB — but if `synchronize` already applied the change, the generated migration will be empty, and the real schema change will never be captured in version control.
3. The feature comment in the file itself acknowledges this risk ("can silently drop columns") for production but misses that the same risk applies in development for migration integrity.

The project's own decision log (D-04, D-08) establishes that schema is controlled exclusively by migrations run via `migration:run`. `synchronize: true` contradicts that decision even in development.

**Fix:** Set `synchronize: false` unconditionally. Developers should always use `migration:run` to advance their local schema:

```typescript
// src/app.module.ts
useFactory: (cfg: ConfigService) => ({
  type: 'postgres',
  url: cfg.get<string>('DATABASE_URL'),
  entities: [UserEntity, EventEntity],
  migrations: [__dirname + '/database/migrations/*{.ts,.js}'],
  synchronize: false, // NEVER enable; always use migration:run
  migrationsRun: false,
  logging: cfg.get<string>('NODE_ENV') === 'development',
}),
```

## Warnings

### WR-01: Runtime Migrations Glob Includes `.ts` Source Files

**File:** `src/app.module.ts:22`

**Issue:** The `migrations` path in the NestJS TypeORM config is:

```
__dirname + '/database/migrations/*{.ts,.js}'
```

Since `migrationsRun: false`, NestJS never executes this path at application startup, so there is no immediate runtime failure. However the glob is misleading and poses two risks:

1. If `migrationsRun` is ever flipped to `true` (a common next step), NestJS will attempt to load `.ts` source files from within the compiled `dist/` output, where they do not exist. The glob will silently match nothing and no migrations will run — or it will fail with a module resolution error depending on the TypeScript setup.
2. The CLI `data-source.ts` (correct) already demonstrates the right pattern: point only to `dist/**/*.js`. Having two different patterns for the same migrations directory increases the chance of divergence.

**Fix:** Align the runtime migrations path with the CLI data-source pattern, targeting only compiled JS files:

```typescript
migrations: [__dirname + '/database/migrations/*.js'],
```

Alternatively, use the `migrations` array with explicit imports, which is the most robust approach:

```typescript
import { Baseline1745000000000 } from './database/migrations/1745000000000-baseline';
// ...
migrations: [Baseline1745000000000],
```

### WR-02: `main.ts` Reads Raw `process.env.PORT` Instead of Validated ConfigService Value

**File:** `src/main.ts:51`

**Issue:**

```typescript
await app.listen(process.env.PORT ?? 3000);
```

`process.env.PORT` is always a `string` (or `undefined`). The validated `EnvironmentVariables.PORT` from `env.validation.ts` is typed as `number` and has already been coerced and bounds-checked (Min 1, Max 65535). By reading `process.env` directly, this line bypasses the validated config entirely:

- If `PORT` is set to an out-of-range string like `"99999"`, the config validation in `ConfigModule` will throw on bootstrap — but if it somehow doesn't (e.g., the validation runs after `listen()`), `app.listen()` would receive an invalid port.
- The raw string `"3000"` passed to `app.listen()` works because the underlying `http.Server.listen()` accepts strings, but it is inconsistent with the rest of the application which relies on `ConfigService` for all env access.

**Fix:** Inject `ConfigService` into the bootstrap function and use the validated port:

```typescript
// src/main.ts
import { ConfigService } from '@nestjs/config';

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  // ... setup ...

  const configService = app.get(ConfigService);
  const port = configService.get<number>('PORT') ?? 3000;
  await app.listen(port);
}
```

## Info

### IN-01: `@DeleteDateColumn({ nullable: true })` — Redundant Option

**File:** `src/events/event.entity.ts:74`

**Issue:** `@DeleteDateColumn` is inherently nullable — TypeORM stores `null` when a row is not soft-deleted and sets a timestamp only on `softDelete()`. Passing `{ nullable: true }` is redundant and may give the impression that there is a meaningful configuration choice being made here.

**Fix:** Remove the option to reduce noise:

```typescript
@DeleteDateColumn()
deletedAt: Date | null;
```

### IN-02: No Foreign Key Constraint on `events.organizerId` in Baseline Migration

**File:** `src/database/migrations/1745000000000-baseline.ts:43`

**Issue:** The `events` table has an `organizerId` column that is semantically a foreign key to `users.id`, but no `CONSTRAINT "FK_events_organizerId" FOREIGN KEY ("organizerId") REFERENCES "users"("id")` is declared. Likewise, `categoryId` references no declared `categories` table FK.

This is not necessarily a bug — nullable FK columns without DB-level constraints are a common pragmatic choice, and `categoryId` may intentionally defer the categories domain to a later phase. However the absence is worth a conscious acknowledgment:

- Without a DB FK, no referential integrity check prevents an `organizerId` pointing to a deleted or non-existent user.
- TypeORM's `@ManyToOne` / `@JoinColumn` decorators would normally generate these constraints; since the entity uses raw `@Column` for `organizerId`, the constraint must be added manually to the migration when the relationship is formalized.

**Fix:** No immediate action required if deferring the FK to when the `User` ↔ `Event` relationship decorator is added. Document the intent in the entity:

```typescript
// Intentionally no FK constraint — relationship formalized in Phase X
// when @ManyToOne(() => UserEntity) is added.
@Column({ type: 'varchar', length: 30, nullable: true })
organizerId: string | null;
```

### IN-03: Entity Spec Tests Use `'field' in entity` — Will Not Catch Decorator Regressions

**File:** `src/events/event.entity.spec.ts:39-43`, `src/users/user.entity.spec.ts:32-35`

**Issue:** The field-shape tests verify property existence with `'field' in entity`:

```typescript
expect('deletedAt' in event).toBe(true);
```

Because `deletedAt` is declared as a class property (TypeScript instance field), `'deletedAt' in event` is `true` even if all TypeORM decorators are stripped from the file. These tests do not validate that `@DeleteDateColumn`, `@Column`, etc. are correctly applied — only that the TypeScript property declaration exists.

A future refactor that accidentally removes `@DeleteDateColumn` (breaking soft-delete) while keeping the `deletedAt: Date | null` property declaration would pass these tests.

**Fix:** Either supplement with TypeORM metadata checks (using `getMetadataArgsStorage()`) or replace the `'in'` assertions with checks that verify default values or decorator behavior. For example, the `generateId` tests already do this well by calling `event.generateId()` and asserting on observable behavior. Extend that pattern:

```typescript
it('should default status to DRAFT', () => {
  const event = new EventEntity();
  // TypeORM applies column defaults during insert, not construction,
  // but the enum constant is accessible:
  expect(EventStatus.DRAFT).toBe('DRAFT');
  // A more meaningful check: ensure the property is not accidentally removed
  expect(Object.prototype.hasOwnProperty.call(EventEntity.prototype, 'generateId')).toBe(true);
});
```

Or accept the current tests as smoke-level coverage and document the limitation.
