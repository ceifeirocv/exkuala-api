# Phase 1.1 Learnings: Migrate from Prisma to TypeORM

> **Root-cause flag:** The code review (`1.1-REVIEW.md`, CR-01) flagged `synchronize: true` in development as a **critical** issue at this phase, predicting the exact schema-drift failure that later struck Phases 7 and 8. The fix (`synchronize: false` unconditionally) was **not applied** — the phase shipped and passed verification 4/4. See the first surprise below. Captured durably in memory `[[typeorm-synchronize-constraint-drift]]`.

## Decisions

### App-generated CUID PK via `@PrimaryColumn` + `@BeforeInsert`
Entities use `@PrimaryColumn` (varchar 30) with a `@BeforeInsert generateId()` calling `createId()` — not `@PrimaryGeneratedColumn`.

**Rationale:** IDs are generated in app code (cuid2), not by Postgres; keeps PK generation portable and deterministic. Note the lifecycle-hook caveat that later bit Phase 8 (`@BeforeInsert` skipped on QB/`insert()`).
**Source:** 1.1-03-SUMMARY.md, 1.1-VERIFICATION.md

### `@DeleteDateColumn` for soft delete (not plain nullable `@Column`)
`deletedAt` uses `@DeleteDateColumn` so TypeORM auto-applies `WHERE deletedAt IS NULL`.

**Rationale:** Replicates Prisma soft delete with built-in query filtering, unlike Phase 1's Prisma setup which required manual `where: { deletedAt: null }`.
**Source:** 1.1-03-SUMMARY.md

### Explicit `enumName: 'event_status'`
The status enum column pins its PostgreSQL type name.

**Rationale:** Prevents TypeORM auto-generated enum type names from colliding / duplicate-type errors. This decision recurs in Phases 5 and 8 — a standing project rule for every enum column.
**Source:** 1.1-03-SUMMARY.md

### Decimal transformer coercing pg string → number
`ticketPrice` uses a column transformer applying `parseFloat`.

**Rationale:** The pg driver returns `DECIMAL` as a string; the transformer restores a `number` at the entity boundary.
**Source:** 1.1-03-SUMMARY.md, 1.1-VERIFICATION.md

### Separate CLI DataSource from the NestJS module
`src/database/data-source.ts` reads `process.env` directly (no NestJS/ConfigService) and globs `dist/**/*.entity.js` + `dist/database/migrations/*.js`; `synchronize: false` hardcoded.

**Rationale:** The TypeORM CLI runs outside the Nest container; `nodenext` prevents loading `.ts` sources, so the CLI must point at compiled `dist`. Two configs (CLI + module) share one schema.
**Source:** 1.1-04-SUMMARY.md, 1.1-VERIFICATION.md

### Single squashed baseline migration (D-03)
One hand-written `1745000000000-baseline.ts` recreates the full schema (users + events + `event_status`); `prisma/` deleted as the former source of truth.

**Rationale:** A clean migration history start under TypeORM rather than translating Prisma's migration files; fixed timestamp keeps the class name/filename aligned.
**Source:** 1.1-04-SUMMARY.md, 1.1-05-SUMMARY.md

### `synchronize` gated to `NODE_ENV === 'development'`, `migrationsRun: false` **[review-contested]**
The module enables `synchronize` in dev only; migrations are CLI-only via `migration:run` (D-04, D-08).

**Rationale (as shipped):** Convenience in dev, migration-controlled prod. **Contested:** CR-01 argued this contradicts D-04/D-08 even in dev and undermines migration integrity — and it did, in Phases 7–8. The defensible choice was `synchronize: false` unconditionally.
**Source:** 1.1-05-SUMMARY.md, 1.1-REVIEW.md (CR-01)

### `transformIgnorePatterns` allowlist for ESM deps in Jest
Jest config allowlists `@paralleldrive/cuid2`, `@noble/hashes` (and `@noble/ciphers`) through ts-jest transformation.

**Rationale:** These are ESM-only; Jest's default `transformIgnorePatterns` excludes all of `node_modules`, causing "Cannot use import statement outside a module". Required in both unit and e2e configs.
**Source:** 1.1-03-SUMMARY.md, 1.1-06-SUMMARY.md

### Build-first migration scripts
`migration:run` etc. run `build` first, then invoke the TypeORM CLI against `dist/database/data-source.js`.

**Rationale:** The CLI consumes compiled JS (dist globs), so the build must precede it.
**Source:** 1.1-02-SUMMARY.md

## Lessons

### ESM-only `cuid2`/`@noble/hashes` break Jest by default — in every Jest config
The ESM packages threw `SyntaxError: Cannot use import statement outside a module`; fixed by `transformIgnorePatterns`. The unit config and the **separate** e2e config (`test/jest-e2e.json`) each needed the fix independently.

**Context:** A multi-config repo must apply the same ESM allowlist everywhere; fixing only the unit config left e2e broken until Plan 06.
**Source:** 1.1-03-SUMMARY.md, 1.1-06-SUMMARY.md

### A critical, correct review finding was shipped unfixed
CR-01 (`synchronize: true` in dev) was rated **critical**, came with the exact predicted failure ("local DB schema silently diverged… generated migration will be empty"), and a one-line fix — yet the phase shipped with the option enabled and passed verification.

**Context:** Verification checks "matches the plan"; it does not re-litigate a review finding the plan chose not to adopt. A critical review item needs an explicit accept/reject gate, or it silently survives. This one's predicted cost landed in Phases 7–8.
**Source:** 1.1-REVIEW.md (CR-01), 1.1-VERIFICATION.md

### Removing an ORM is a multi-step teardown with ordering hazards
The Prisma removal hit three ordering traps: the `postinstall: prisma generate` hook had to be deleted *before* uninstalling Prisma; blocking source files (`prisma.service.ts` importing removed packages) had to be deleted before `build` would pass (Plan 04 did this early with a stub comment handing off to Plan 05); and removing the `postinstall` line left an invalid trailing comma in `package.json`.

**Context:** Dependency swaps need a deliberate teardown order — hooks, then importers, then packages — or each step blocks the next.
**Source:** 1.1-02-SUMMARY.md, 1.1-04-SUMMARY.md

### Entity spec tests using `'field' in entity` can't catch decorator regressions
The field-shape assertions (`'deletedAt' in event`) pass even if every TypeORM decorator is stripped, because the TypeScript instance field still exists (IN-03).

**Context:** Property-existence checks give false confidence; soft-delete/enum correctness needs metadata assertions or observable-behavior tests (as the `generateId` tests do).
**Source:** 1.1-REVIEW.md (IN-03)

### Two divergent migrations globs for one directory is a latent trap
The NestJS module used `*{.ts,.js}` while the CLI DataSource correctly used `dist/**/*.js`; if `migrationsRun` is ever flipped true, the module glob would match nothing in `dist` (WR-01).

**Context:** Keep one canonical migrations path pattern (compiled `.js`); divergent patterns for the same directory invite a silent "no migrations ran" failure.
**Source:** 1.1-REVIEW.md (WR-01)

## Patterns

### Wave 0 entity spec stubs (TDD RED)
Entity specs written before the entities exist, failing with "Cannot find module", driving the later implementation plan.

**When to use:** Opening wave of any TDD phase — consistent across the whole project.
**Source:** 1.1-01-SUMMARY.md

### Squashed baseline migration on ORM swap
Replace the prior ORM's migration history with one hand-written baseline that recreates the live schema, then delete the old ORM's migration files.

**When to use:** Migrating ORMs (or resetting migration history) where translating individual historical migrations adds no value.
**Source:** 1.1-04-SUMMARY.md

### Dual config: CLI DataSource (`process.env`) + module `forRootAsync` (ConfigService)
A standalone CLI DataSource over raw env for migrations, plus the NestJS `TypeOrmModule.forRootAsync` over ConfigService for the running app — both describing the same schema.

**When to use:** TypeORM projects needing CLI migrations independent of the Nest bootstrap.
**Source:** 1.1-04-SUMMARY.md, 1.1-05-SUMMARY.md

### `transformIgnorePatterns` allowlist for ESM dependencies
Allowlist specific ESM-only `node_modules` packages through the transformer in each Jest config.

**When to use:** Any Jest suite importing ESM-only deps (cuid2, noble) — apply to unit *and* e2e configs.
**Source:** 1.1-03-SUMMARY.md, 1.1-06-SUMMARY.md

### `enumName` anti-collision on every enum column
Always pin the PostgreSQL enum type name on `@Column({ type: 'enum', enumName })`.

**When to use:** Every TypeORM enum column (recurs in Phases 5 and 8).
**Source:** 1.1-03-SUMMARY.md

### Early teardown with stub-comment handoff between plans
Plan 04 deleted the Prisma files blocking its build early (a subset of Plan 05's scope) and left a stub comment in `app.module.ts` guiding Plan 05 to finish the wiring.

**When to use:** When a later plan owns a change but an earlier plan is blocked without part of it — do the minimal subset and hand off explicitly.
**Source:** 1.1-04-SUMMARY.md

## Surprises

### The drift root cause was identified, predicted, and waved through here
`synchronize: true` in dev was caught at the migration phase by code review, rated critical, with the precise failure mode spelled out. It shipped anyway because the plan's D-04 had chosen it and verification only checks plan-conformance. Two phases later the predicted "silent schema divergence" produced the Phase 8 missing-constraints bug and the Phase 8 dropped-`@Unique` bug.

**Impact:** The most expensive recurring DB hazard of the project was a *known, documented, single-line-fixable* decision at Phase 1.1 — not a discovery. Reinforces that critical review findings need an explicit adopt/reject decision, not silent survival. Strengthened memory `[[typeorm-synchronize-constraint-drift]]` with this provenance.
**Source:** 1.1-REVIEW.md (CR-01), 1.1-05-SUMMARY.md, and Phase 8 deviations

### A green entity test suite would survive removal of the decorators it "tests"
The soft-delete and field-shape specs assert `'field' in entity`, which holds even if `@DeleteDateColumn` and every other decorator are deleted — the suite passes while the behavior it nominally guards is gone.

**Impact:** "14/14 green" for the migration overstated confidence; the tests prove TypeScript properties exist, not that TypeORM mappings are correct. Behavior/metadata assertions are needed for true regression safety.
**Source:** 1.1-REVIEW.md (IN-03)
