## Summary

The implementation covers the Auth0 webhook endpoint with secret-header guard, upsert service, and env validation. The core threat mitigations (T-01/T-02 timing-safe compare with length pre-check, T-04 required env var at startup, T-05 parameterized upsert) are structurally present.

Two correctness issues found: the `sub` field accepts empty strings through validation (bypasses the guard's own empty-string rejection only for the header, not for the body payload), and the guard returns `false` producing a 403 instead of 401 for an authentication check. Three additional warnings cover the `@IsString()` bypass gap, the upsert silently swallowing database errors, and a timing-oracle leak introduced by the string-length early return.

## Critical Issues

### CR-01: Length-based early return leaks timing information on the guard

**File:** `src/webhooks/guards/webhook-secret.guard.ts:27-29`
**Issue:** The guard returns `false` immediately when `incomingSecret.length !== expectedSecret.length`. This is the exact timing oracle that `timingSafeEqual` is designed to prevent. An attacker can binary-search the correct secret length by measuring response latency: mismatched-length requests return faster than same-length requests that go through the full byte comparison. For a shared secret used as the sole authentication mechanism on this endpoint, length disclosure narrows the brute-force space significantly.

The comment cites "RESEARCH.md Pitfall 2" (timingSafeEqual throws TypeError on differing byte lengths) as the justification, but that pitfall is solved by padding to the longer length before comparison — not by early-returning.

**Fix:**
```typescript
// Pad both buffers to the same length with zeroes before comparing.
// This preserves constant-time behaviour: timingSafeEqual always sees equal-length inputs.
// The all-zero padding is not guessable, so a padded mismatch still produces false.
const maxLen = Math.max(incomingSecret.length, expectedSecret.length);
const a = Buffer.alloc(maxLen);
const b = Buffer.alloc(maxLen);
Buffer.from(incomingSecret).copy(a);
Buffer.from(expectedSecret).copy(b);
return timingSafeEqual(a, b);
```

## Warnings

### WR-01: `sub` field accepts empty strings — no `@IsNotEmpty()` guard

**File:** `src/webhooks/dto/auth0-webhook.dto.ts:8-9`
**Issue:** `@IsString()` passes validation for `""`. If Auth0 sends an empty `sub` (or an attacker crafts a request with `sub: ""`), `upsertFromAuth0("")` is called and a user row with `auth0Id = ""` is written to the database. This is a valid unique value in the schema (no `CHECK (auth0Id != '')` constraint exists in the migration). Subsequent calls with `sub: ""` would all resolve to the same phantom user, which could become an authorization confusion issue if roles or data are ever scoped by `auth0Id`.

**Fix:**
```typescript
@IsString()
@IsNotEmpty()
sub: string;
```

### WR-02: Guard returns `false` (403 Forbidden) for an authentication failure

**File:** `src/webhooks/guards/webhook-secret.guard.ts:10`
**Issue:** When the guard rejects the request, NestJS translates `canActivate` returning `false` into a **403 Forbidden** response. The correct HTTP status for a missing or invalid authentication credential is **401 Unauthorized**. This is a semantic correctness issue: RFC 7235 §3.1 specifies 401 when authentication is absent or invalid. Auth0's Action retry logic may not treat 403 as a retryable auth failure the same way it would treat 401, potentially causing silent delivery failures rather than credential-refresh retries. (Flagged by verifier as a known deviation — including here because the HTTP semantics are wrong and the downstream retry behavior is a real risk.)

**Fix:** Throw `UnauthorizedException` instead of returning `false`:
```typescript
import { CanActivate, ExecutionContext, Injectable, UnauthorizedException } from '@nestjs/common';

// ...inside canActivate, replace all `return false` with:
throw new UnauthorizedException('Invalid or missing webhook secret');
```

### WR-03: Database errors from `upsertFromAuth0` are silently swallowed by the controller

**File:** `src/webhooks/webhooks.controller.ts:19-21`
**Issue:** The controller `await`s the service call but has no error handling. If the database is unavailable, the upsert throws a TypeORM error that propagates to NestJS's default exception filter, which returns a 500. This causes Auth0 to retry the webhook. The problem is not the retry itself — it is that there is no logging at the service or controller layer. When the 500 occurs in production, the failure is invisible: no structured log entry, no context about which `sub` failed, no way to distinguish a transient DB outage from a schema mismatch. The CLAUDE.md convention requires structured JSON logging for observability.

**Fix:** Add a try/catch in the service with a structured log, or use a NestJS interceptor/filter to log webhook failures with the relevant `sub` value before re-throwing:
```typescript
async upsertFromAuth0(sub: string): Promise<void> {
  try {
    await this.userRepository.upsert(
      { id: createId(), auth0Id: sub },
      { conflictPaths: ['auth0Id'] },
    );
  } catch (err) {
    // Structured log so the failure is observable; re-throw so caller gets 500
    // and Auth0 retries.
    this.logger.error({ event: 'upsert_failed', sub, error: err.message });
    throw err;
  }
}
```

## Info

### IN-01: `WEBHOOK_SECRET` accepts a single-character value — no minimum-length constraint

**File:** `src/config/env.validation.ts:25-26`
**Issue:** `@IsString()` passes for any non-empty string, including `"x"`. The env validator enforces presence (T-04) but not entropy. A one-character secret is trivially brute-forceable even with constant-time comparison. This is an operational concern rather than a code bug, but the validation layer is the right place to enforce a minimum length so weak secrets fail fast at startup.

**Fix:**
```typescript
@IsString()
@MinLength(32)
WEBHOOK_SECRET!: string;
```
