# Phase 02.1: Add a webhook endpoint for Auth0 to add or refresh user on create/login - Context

**Gathered:** 2026-05-02
**Status:** Ready for planning

<domain>
## Phase Boundary

Deliver an HTTP endpoint that Auth0 Actions call (via POST) when a user registers or logs in. The endpoint validates a shared secret header, upserts a local `users` row keyed on `auth0Id`, and returns 200. This is the primary user creation path; Phase 3 will attach the DB user to `req.user` and use upsert only as a fallback.

**In scope:**
- `WebhookController` with a single `POST /webhooks/auth0` endpoint
- `WebhookSecretGuard` — validates `x-webhook-secret` header against `WEBHOOK_SECRET` env var
- `UsersService.upsertFromAuth0(sub: string)` — INSERT ... ON CONFLICT (auth0Id) DO UPDATE
- DTO: `Auth0WebhookDto` with `sub: string` and `event: 'post-login' | 'post-register'`
- `WEBHOOK_SECRET` added as required env var in `env.validation.ts`
- Unit tests for guard + service upsert logic

**Out of scope:**
- Adding email/name columns to UserEntity (stays minimal — Phase 02.1 only stores auth0Id)
- Attaching DB user to `req.user` in JwtStrategy (Phase 3)
- Any user-facing feature endpoints
- HMAC signature validation (simple header secret is sufficient)

</domain>

<decisions>
## Implementation Decisions

### Webhook Security

- **D-01:** Auth0 Action sends `x-webhook-secret` header containing a shared secret value. New env var: `WEBHOOK_SECRET`.
- **D-02:** `WebhookSecretGuard` implements `CanActivate`. Reads header with `req.headers['x-webhook-secret']`, compares to `ConfigService.get('WEBHOOK_SECRET')` using `crypto.timingSafeEqual` to prevent timing attacks.
- **D-03:** Webhook route is decorated `@Public()` to bypass global `JwtAuthGuard`, then `@UseGuards(WebhookSecretGuard)` for secret validation. Two guards, clean separation.
- **D-04:** Header name: `x-webhook-secret`. Auth0 Action sets this header in its POST call.

### Payload Shape

- **D-05:** Request body shape: `{ sub: string, event: 'post-login' | 'post-register' }`. Auth0 Action extracts `event.user.user_id` → `sub`. DTO uses `class-validator` (`@IsString()`, `@IsIn([...])`) matching existing validation patterns.
- **D-06:** UserEntity stays minimal — `auth0Id` + timestamps only. No new columns in Phase 02.1.

### Response Codes

- **D-07:** 200 OK on both create and update (upsert). Auth0 Action does not need to distinguish.
- **D-08:** 500 on DB error — lets Auth0 retry the webhook. NestJS default exception filter handles this automatically.

### Upsert Semantics

- **D-09:** Upsert key: `auth0Id` (unique constraint already on `UserEntity`). TypeORM `save()` with `{ conflict: ['auth0Id'] }` or query builder `INSERT ... ON CONFLICT (auth0Id) DO UPDATE SET updatedAt = NOW()`. Idempotent — safe for Auth0 retries.

### Phase 3 Impact

- **D-10:** Phase 3's primary job becomes: load local `UserEntity` in `JwtStrategy.validate()` by `sub` and attach to `req.user`. Phase 02.1 is the primary creation path.
- **D-11:** JwtStrategy fallback: if DB lookup returns null (webhook missed or timing race), upsert the user on the spot and return the new record. Belt-and-suspenders — no user ever gets 401 due to a missed webhook.

### Claude's Discretion

- Where inside `src/` to place the webhook module (e.g. `src/webhooks/` alongside `src/auth/`)
- Whether `WebhookSecretGuard` lives in `src/auth/guards/` or `src/webhooks/`
- Exact TypeORM upsert syntax (save vs query builder)
- Test fixture approach for guard unit tests

</decisions>

## Existing Code Insights

### Reusable Assets
- `src/auth/decorators/public.decorator.ts` — `@Public()` sets `IS_PUBLIC_KEY` metadata; apply on webhook controller/method to bypass `JwtAuthGuard`
- `src/config/env.validation.ts` — `EnvironmentVariables` class with `@IsString()` fields; add `WEBHOOK_SECRET` using the same pattern
- `src/users/user.entity.ts` — `UserEntity` with `auth0Id` varchar(128) unique; upsert target already exists

### Established Patterns
- `@Public()` + guard bypass via `Reflector` — already implemented in `JwtAuthGuard`; webhook route follows same pattern
- `forRootAsync({ inject: [ConfigService], useFactory })` — existing pattern for async config in modules
- `class-validator` + `class-transformer` — single validation library for DTOs; use `@IsString()`, `@IsIn()` for webhook DTO
- `crypto.timingSafeEqual` — Node.js built-in; no extra dependency for secret comparison

### Integration Points
- `src/app.module.ts` — Add `WebhooksModule` to `imports[]`
- `src/config/env.validation.ts` — Add `WEBHOOK_SECRET` required field
- `src/users/` — Add or extend `UsersService` with `upsertFromAuth0(sub: string)`; `UsersModule` must export `UsersService` for use in `WebhooksModule`

</code_context>

<specifics>
## Specific Ideas

- Auth0 Action code (not our API code, but the planner should document it): extract `event.user.user_id` as `sub`, set `event` to `'post-register'` or `'post-login'` per trigger type, POST to `https://<api>/webhooks/auth0` with `x-webhook-secret` header and JSON body.
- `timingSafeEqual` requires both buffers to be the same length — guard should handle length mismatch explicitly (return false, not throw).
- `AUTH0_NAMESPACE` is `https://exkuala.cv/roles` (note `.cv` TLD, not `.app`) — confirmed in Phase 2 CONTEXT.md D-03.

</specifics>

<deferred>
## Deferred Ideas

- HMAC-SHA256 signature validation (sign payload body with secret) — more secure against replay attacks, but adds complexity to Auth0 Action code. Revisit if security posture requires it.
- Capturing email/name at webhook time — deferred; extend UserEntity in a later phase when downstream features need it.
- Auth0 Management API integration for back-filling existing users — out of scope for v1.

</deferred>
