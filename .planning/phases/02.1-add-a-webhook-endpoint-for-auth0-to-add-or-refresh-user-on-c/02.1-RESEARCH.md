## Summary

Phase 02.1 delivers a single POST endpoint at `/webhooks/auth0` that Auth0 Actions call on user registration and login events. The endpoint requires two interacting concerns: bypassing the global `JwtAuthGuard` (via `@Public()`) while enforcing a separate shared-secret guard (`WebhookSecretGuard`). This two-guard composition is idiomatic NestJS and follows the exact pattern already used in the project for `@Public()` bypass.

The user creation logic lives in `UsersService.upsertFromAuth0(sub: string)`. TypeORM 0.3.28 — already installed — provides `repository.upsert()` which generates `INSERT ... ON CONFLICT (auth0Id) DO UPDATE SET updatedAt = CURRENT_TIMESTAMP` directly against PostgreSQL. This is the correct API choice over `save()` because `save()` does a SELECT-then-INSERT/UPDATE in two queries, while `upsert()` is a single atomic operation that handles race conditions correctly.

The key implementation hazard is `crypto.timingSafeEqual`: it throws a `TypeError` if input buffers have different byte lengths rather than returning `false`. The guard must guard against this with an early-length-check before comparing. Every other concern — DTO validation, ConfigService injection, module exports, test patterns — maps directly onto established project patterns already present in `src/auth/`.

**Primary recommendation:** Place `WebhooksModule` at `src/webhooks/`, co-locate `WebhookSecretGuard` and `Auth0WebhookDto` there, import `UsersModule` (after adding `exports: [UsersService]`), and register `WebhooksModule` in `AppModule.imports[]`.

### Pattern 1: WebhookSecretGuard with timingSafeEqual

**What:** `CanActivate` guard that compares the `x-webhook-secret` header to `WEBHOOK_SECRET` env var using constant-time comparison. Must handle length mismatch explicitly.

**When to use:** Any route that accepts inbound webhook calls from a trusted sender using a shared secret.

**Example:**

```typescript
// Source: Node.js built-in crypto docs + Context7 /nestjs/docs.nestjs.com guard pattern
import { CanActivate, ExecutionContext, Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import { timingSafeEqual } from 'crypto';
import type { Request } from 'express';

@Injectable()
export class WebhookSecretGuard implements CanActivate {
  constructor(private readonly config: ConfigService) {}

  canActivate(context: ExecutionContext): boolean {
    const req = context.switchToHttp().getRequest<Request>();
    const incomingSecret = req.headers['x-webhook-secret'];
    const expectedSecret = this.config.get<string>('WEBHOOK_SECRET');

    // Both must be strings (not undefined/array) and non-empty
    if (
      typeof incomingSecret !== 'string' ||
      typeof expectedSecret !== 'string' ||
      incomingSecret.length === 0 ||
      expectedSecret.length === 0
    ) {
      return false;
    }

    // timingSafeEqual throws TypeError if byte lengths differ — must check first
    // [VERIFIED: Node.js runtime] — confirmed throws "Input buffers must have the same byte length"
    if (incomingSecret.length !== expectedSecret.length) {
      return false;
    }

    return timingSafeEqual(
      Buffer.from(incomingSecret),
      Buffer.from(expectedSecret),
    );
  }
}
```

### Pattern 3: WebhookController with @Public() and @UseGuards()

**What:** Controller that bypasses global `JwtAuthGuard` via `@Public()` then applies `WebhookSecretGuard` at the method level.

**Example:**

```typescript
// Source: Context7 /nestjs/docs.nestjs.com — guard composition

import { Public } from '../auth/decorators/public.decorator';
import { Auth0WebhookDto } from './dto/auth0-webhook.dto';

@Controller('webhooks')
export class WebhookController {
  constructor(private readonly usersService: UsersService) {}

  @Public()
  @UseGuards(WebhookSecretGuard)
  @Post('auth0')
  @HttpCode(200)
  async handleAuth0Webhook(@Body() dto: Auth0WebhookDto): Promise<void> {
    await this.usersService.upsertFromAuth0(dto.sub);
  }
}
```

### Anti-Patterns to Avoid

- **Re-registering APP_GUARD in WebhooksModule:** `JwtAuthGuard` and `RolesGuard` are already registered as `APP_GUARD` in `AuthModule`. Adding them again in `WebhooksModule` causes double-execution on all routes. Never re-register APP_GUARD providers.
- **Using `save()` for upsert:** `repository.save({ auth0Id: sub })` does a SELECT first to check existence, then INSERT or UPDATE. Not atomic. Use `repository.upsert()` instead.
- **Using `@BeforeInsert` for id generation on upsert path:** `@BeforeInsert` fires on `save()` / `insert()` but NOT on `upsert()`. The `upsert()` call must supply the `id` explicitly, OR you rely on the fact that on conflict (existing row) no new id is needed. For new rows via `upsert()`, cuid2 id must be pre-generated in the service before calling `upsert()`.
- **Placing `@UseGuards(WebhookSecretGuard)` before `@Public()`:** Decorator order does not affect guard execution order for Nest's HTTP pipeline — all route-level guards run after global guards. The `@Public()` metadata key is read by the global `JwtAuthGuard`, which short-circuits before `WebhookSecretGuard` runs. The stacking order of `@Public()` and `@UseGuards()` decorators on the same handler does not matter.
- **Calling `timingSafeEqual` with unequal-length buffers:** This throws `TypeError` at runtime. Always check `incomingSecret.length !== expectedSecret.length` before calling.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic insert-or-update | Custom SELECT + INSERT/UPDATE | `repository.upsert(entity, { conflictPaths })` | Race condition between SELECT and INSERT; upsert is atomic at DB level |
| Constant-time comparison | `===` string equality | `crypto.timingSafeEqual` | Timing oracle attack: `===` returns early on first mismatched byte, leaking secret length |
| DTO validation | Manual `if (!body.sub)` checks | `class-validator` with `ValidationPipe` | Global pipe already configured; add decorators to DTO class and get 400 with structured errors for free |
| Config access in guard | `process.env.WEBHOOK_SECRET` | `ConfigService.get('WEBHOOK_SECRET')` | ConfigService is validated at startup; `process.env` is unvalidated and may be undefined silently |

**Key insight:** The global `ValidationPipe` (already registered in `main.ts` or `AppModule`) handles DTO validation automatically. The guard handles only the secret-header concern. These are orthogonal.

## Common Pitfalls

### Pitfall 1: @BeforeInsert does not fire on repository.upsert()

**What goes wrong:** `UserEntity.generateId()` is decorated with `@BeforeInsert()`. When `repository.upsert()` is called for a new user (no conflict), `@BeforeInsert` does NOT fire — TypeORM's upsert bypasses entity lifecycle hooks. The `id` column will be NULL/undefined on insert, violating the `NOT NULL` constraint and crashing.

**Why it happens:** `repository.upsert()` generates raw SQL and does not instantiate entity objects or trigger hooks. `@BeforeInsert` is only triggered by `repository.save()` and `repository.insert()`.

**How to avoid:** Pre-generate the cuid2 id in the service method before calling `upsert()`:

```typescript
import { createId } from '@paralleldrive/cuid2';

async upsertFromAuth0(sub: string): Promise<void> {
  await this.userRepository.upsert(
    { id: createId(), auth0Id: sub },
    { conflictPaths: ['auth0Id'] },
  );
  // On conflict: id is from EXCLUDED row but not used (ON CONFLICT DO UPDATE
  // only touches updatedAt). The existing row's id is preserved.
}
```

**Warning signs:** `null value in column "id" of relation "users" violates not-null constraint` error in logs.

### Pitfall 2: timingSafeEqual throws on length mismatch

**What goes wrong:** Guard calls `crypto.timingSafeEqual(Buffer.from(incomingSecret), Buffer.from(expectedSecret))` when the two strings have different byte lengths. Node.js throws `TypeError: Input buffers must have the same byte length` — this becomes an unhandled exception and a 500, not a 401.

**Why it happens:** The function is designed for values that are always the same length (e.g., HMAC digests). Simple secrets of arbitrary length require an explicit length gate.

**How to avoid:** Return `false` before calling `timingSafeEqual` if lengths differ (see Pattern 1 above). [VERIFIED: Node.js runtime]

### Pitfall 3: Global ValidationPipe requires whitelist mode awareness

**What goes wrong:** If the global `ValidationPipe` is configured with `{ whitelist: true }`, extra properties in the body (e.g., other Auth0 JWT fields) are stripped before reaching the controller. This is correct behavior and safe here. If `{ forbidNonWhitelisted: true }` is also set, extra properties cause a 400.

**Why it happens:** Auth0 Actions can be configured to send additional fields. Check `main.ts` for ValidationPipe configuration.

**How to avoid:** Either configure the DTO to accept only `sub` and `event`, or verify the Auth0 Action sends only those fields. Stripping extras is fine; forbidding them may be fragile.

**Action:** Check `main.ts` `ValidationPipe` options. If `forbidNonWhitelisted: true`, ensure Auth0 Action sends exactly the fields in the DTO.

### Pitfall 4: APP_GUARD execution order with @UseGuards()

**What goes wrong:** Developer assumes `@UseGuards(WebhookSecretGuard)` on the route handler means `WebhookSecretGuard` runs before `JwtAuthGuard`. This is backwards. Global `APP_GUARD` providers (bound via `AuthModule`) run first in registration order.

**Why it happens:** NestJS guard execution order: `APP_GUARD` providers run before `@UseGuards()` route-level guards.

**How to avoid:** The existing `JwtAuthGuard` checks for `@Public()` metadata and returns `true` when found — it short-circuits cleanly. By the time `WebhookSecretGuard` runs, JWT validation has already been skipped. This is the correct and intended behavior for D-03.

**Execution sequence on a `@Public()` route:**
1. `JwtAuthGuard.canActivate()` — sees `@Public()`, returns `true` immediately
2. `RolesGuard.canActivate()` — sees `@Public()` (it also checks IS_PUBLIC_KEY), returns `true` immediately
3. `WebhookSecretGuard.canActivate()` — performs header comparison, returns `true` or `false`
4. Controller method executes (only if all guards returned `true`)

### Pitfall 5: UsersModule not exporting UsersService

**What goes wrong:** `WebhooksModule` imports `UsersModule` but cannot inject `UsersService` — NestJS throws `Nest can't resolve dependencies of the WebhookController (?). Please make sure that the argument UsersService at index [0] is available in the WebhooksModule context`.

**Why it happens:** NestJS module encapsulation. A service must be in the `exports` array of its module to be available to importers.

**How to avoid:** Add `exports: [UsersService]` to `UsersModule`. This is a required change that must be part of the plan.

### Pitfall 6: RolesGuard does not check IS_PUBLIC_KEY

**Verify:** Read `src/auth/guards/roles.guard.ts` before assuming this guard also short-circuits on `@Public()`. If it does not, a `@Public()` route with `@UseGuards(WebhookSecretGuard)` could fail at the RolesGuard step (no user on request → roles check fails). Looking at the test file, `roles.guard.spec.ts` line 23-28 shows `RolesGuard` does check `IS_PUBLIC_KEY` — so it will short-circuit correctly. [VERIFIED: src/auth/guards/roles.guard.spec.ts]

## Code Examples

### Auth0 Action code (not API code — runs in Auth0 tenant)

```javascript
// Auth0 Action: "Sync user to API on login/register"
// Trigger: Post Login (covers both registration and login)
// Source: [ASSUMED] — Auth0 Actions JavaScript API pattern

exports.onExecutePostLogin = async (event, api) => {
  const webhookUrl = event.secrets.WEBHOOK_URL; // e.g. https://api.exkuala.cv/webhooks/auth0
  const webhookSecret = event.secrets.WEBHOOK_SECRET;

  // Determine event type (Auth0 post-login fires for both; use login_count to detect register)
  const isNewUser = event.stats.logins_count === 1;
  const webhookEvent = isNewUser ? 'post-register' : 'post-login';

  try {
    await fetch(webhookUrl, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'x-webhook-secret': webhookSecret,
      },
      body: JSON.stringify({
        sub: event.user.user_id,   // e.g. "auth0|abc123"
        event: webhookEvent,
      }),
    });
  } catch (error) {
    // Log but don't block login — user should still be able to log in even if webhook fails
    console.log('Webhook failed:', error.message);
  }
};
```

**Note on Auth0 trigger type:** A single "Post Login" action fires for both login and first registration. The `event.stats.logins_count === 1` check distinguishes registration (first login ever) from subsequent logins. Auth0 also has a dedicated "Post Registration" trigger, but using a single Post Login action is simpler. [ASSUMED] — confirm in Auth0 tenant which trigger type is in use.

### TypeORM upsert with pre-generated id

```typescript
// Source: Context7 /typeorm/typeorm — repository.upsert() + Pitfall 1 fix
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { createId } from '@paralleldrive/cuid2';
import { UserEntity } from './user.entity';

@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(UserEntity)
    private readonly userRepository: Repository<UserEntity>,
  ) {}

  async upsertFromAuth0(sub: string): Promise<void> {
    await this.userRepository.upsert(
      { id: createId(), auth0Id: sub },
      { conflictPaths: ['auth0Id'] },
    );
  }
}
```

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | `WebhookSecretGuard` — shared secret header via `crypto.timingSafeEqual` |
| V3 Session Management | no | Webhook is stateless; no session |
| V4 Access Control | no | Guard is binary allow/deny; no resource-level access control |
| V5 Input Validation | yes | `class-validator` on `Auth0WebhookDto` via global `ValidationPipe` |
| V6 Cryptography | yes | `crypto.timingSafeEqual` — Node.js built-in constant-time comparison; no hand-rolled crypto |

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Timing oracle on secret comparison | Information Disclosure | `crypto.timingSafeEqual` — constant-time comparison regardless of match position |
| Replay attack (resending captured request) | Spoofing | Out of scope for v1 (HMAC+nonce deferred); acceptable given the only action is an idempotent upsert |
| Spoofed sub value | Tampering | Auth0 Action code is only attacker vector; secret header prevents external parties from calling the endpoint |
| Oversized request body | Denial of Service | NestJS/Express default body size limit (100kb) applies; `auth0Id` column is `varchar(128)`, enforced by DB |
