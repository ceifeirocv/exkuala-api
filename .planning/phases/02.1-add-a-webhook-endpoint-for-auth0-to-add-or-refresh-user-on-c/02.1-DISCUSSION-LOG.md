## Webhook Security

| Option | Description | Selected |
|--------|-------------|----------|
| Shared secret header | Auth0 Action sends x-webhook-secret header. 1 new env var, simple to implement. | ✓ |
| Auth0 M2M JWT | Auth0 Action fetches M2M token, sends as Bearer. Reuses JwtAuthGuard infra but more complex Action code. | |
| No auth (obscure URL) | Unauthenticated endpoint. Not recommended for production. | |

**User's choice:** Shared secret header

**Guard placement:**

| Option | Description | Selected |
|--------|-------------|----------|
| Custom guard (WebhookSecretGuard) | CanActivate guard, decoratable with @UseGuards. | ✓ |
| Middleware | NestJS middleware validates header. Less idiomatic. | |
| You decide | Claude picks. | |

**User's choice:** Custom guard

**Guard + JwtAuthGuard interaction:**

| Option | Description | Selected |
|--------|-------------|----------|
| @Public() + WebhookSecretGuard | Bypass global JwtAuthGuard with @Public(), apply WebhookSecretGuard explicitly. | ✓ |
| Separate module, no APP_GUARD | Mount webhook in isolated module outside global guard. | |

**User's choice:** @Public() + WebhookSecretGuard

**Header name:**

| Option | Description | Selected |
|--------|-------------|----------|
| x-webhook-secret | Simple, explicit. | ✓ |
| x-auth0-signature | HMAC-SHA256 signed payload — more secure but complex. | |
| You decide | Claude picks. | |

**User's choice:** x-webhook-secret

**Notes:** None beyond selections.

## Phase 3 Overlap

| Option | Description | Selected |
|--------|-------------|----------|
| Attach DB user to req.user only | Phase 3 loads UserEntity and attaches to req.user. No upsert as primary path. | ✓ |
| Keep upsert in JwtStrategy too | Belt-and-suspenders: JwtStrategy also upserts. Webhook is best-effort. | |
| Phase 3 becomes a no-op | Skip Phase 3 entirely. req.user stays as { sub, roles }. | |

**User's choice:** Attach DB user to req.user only

**Fallback on user not found:**

| Option | Description | Selected |
|--------|-------------|----------|
| Upsert as fallback | If DB lookup returns null, create user row on the spot. Belt-and-suspenders. | ✓ |
| Return 401 | Strict: reject request if user doesn't exist locally. | |
| Pass req.user as undefined | Let request through, feature endpoints handle missing user. | |

**User's choice:** Upsert as fallback

**Notes:** Phase 3 scope is now: load user from DB by sub, attach to req.user, upsert only if webhook missed.

## Error / Retry Behavior

| Option | Description | Selected |
|--------|-------------|----------|
| 200 OK always | Same response for create and update. Auth0 Action doesn't need to differentiate. | ✓ |
| 201 on create, 200 on update | Semantically correct but unnecessary complexity. | |

**User's choice:** 200 OK always

**On DB error:**

| Option | Description | Selected |
|--------|-------------|----------|
| 500 on DB error | Lets Auth0 retry. NestJS default exception filter handles this. | ✓ |
| 200 always, log error | Never fail Auth0 Action; log internally. Auth0 won't retry. | |

**User's choice:** 500 on DB error

**Notes:** Upsert key is auth0Id (unique constraint). No ambiguity — idempotency is guaranteed.
