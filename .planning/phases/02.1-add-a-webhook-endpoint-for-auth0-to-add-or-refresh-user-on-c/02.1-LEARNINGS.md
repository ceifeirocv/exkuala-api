# Phase 2.1 Learnings: Auth0 User-Sync Webhook

> **Code-vs-artifact note:** `02.1-REVIEW.md` raised a CRITICAL timing-oracle finding (CR-01) plus three warnings. Unlike Phase 1.1, these **were applied** — verified in current source: the guard pads to `maxLen` then `timingSafeEqual` (no length early-return), throws `UnauthorizedException` (401), the DTO has `@IsNotEmpty()` on `sub`, and `WEBHOOK_SECRET` carries `@MinLength(32)`. The decisions below reflect the **hardened, shipped** code. Note that `02.1-03-SUMMARY.md` and STATE.md still describe the superseded "length-mismatch early return" — the planning artifacts are stale relative to the code.

## Decisions

### Constant-time secret compare via equal-length padding (not early-return)
The guard pads both secrets to `maxLen` with zeroed buffers, then `timingSafeEqual`.

**Rationale:** `timingSafeEqual` throws on differing byte lengths, but the safe fix is padding to a common length — an early `return false` on length mismatch reintroduces the exact timing oracle the function exists to prevent (CR-01). Padding keeps the comparison constant-time and still rejects mismatches.
**Source:** src/webhooks/guards/webhook-secret.guard.ts, 02.1-REVIEW.md (CR-01)

### Guard throws `UnauthorizedException` (401), not `return false` (403)
Missing/invalid secret yields 401, not the 403 that `canActivate` returning `false` produces.

**Rationale:** RFC 7235 §3.1 — 401 is correct for absent/invalid credentials; Auth0 Action retry logic treats 401 as a retryable auth failure where 403 may be dropped silently (WR-02).
**Source:** src/webhooks/guards/webhook-secret.guard.ts, 02.1-REVIEW.md (WR-02)

### `@Public()` + route-level `@UseGuards(WebhookSecretGuard)` on the handler
The webhook bypasses the global JWT guard (`@Public()`) and enforces a route-specific shared-secret guard.

**Rationale:** Auth0 Actions can't present a user JWT; the endpoint authenticates with a shared header secret instead. Decorator order matters — `@Public()` short-circuits the APP_GUARDs first, then the route guard runs.
**Source:** 02.1-04-SUMMARY.md

### `WebhooksModule` registers only the route guard, no `APP_GUARD`
Providers contain `WebhookSecretGuard` only; the module does not re-register `JwtAuthGuard`/`RolesGuard`.

**Rationale:** Those are already `APP_GUARD` in AuthModule; re-registering would double-execute them on every route in the app.
**Source:** 02.1-04-SUMMARY.md

### `WEBHOOK_SECRET` required env var with `@MinLength(32)`
Validated as a required string of at least 32 chars at boot.

**Rationale:** Presence (T-04) plus entropy — a one-char secret is brute-forceable even with constant-time compare; the validation layer fails weak secrets fast at startup (IN-01).
**Source:** src/config/env.validation.ts, 02.1-02-SUMMARY.md, 02.1-REVIEW.md (IN-01)

### `Auth0WebhookDto`: `@IsString() @IsNotEmpty() sub`, `@IsIn([...]) event`
`sub` must be a non-empty string; `event` is constrained to `post-login`/`post-register`; `whitelist: true` strips extra Auth0 fields.

**Rationale:** `@IsString()` alone passes `""`, which would write a phantom `auth0Id=''` user (WR-01); `@IsNotEmpty()` closes it. Whitelisting silently drops the rest of Auth0's large payload.
**Source:** src/webhooks/dto/auth0-webhook.dto.ts, 02.1-03-SUMMARY.md, 02.1-REVIEW.md (WR-01)

### Idempotent upsert with pre-generated cuid2 id
`upsertFromAuth0(sub)` calls `repository.upsert({ id: createId(), auth0Id: sub }, { conflictPaths: ['auth0Id'] })`.

**Rationale:** Idempotent on repeated Auth0 logins; the id is pre-generated because `repository.upsert()` bypasses `@BeforeInsert` lifecycle hooks.
**Source:** 02.1-02-SUMMARY.md

### `UsersModule` `forFeature` + exports `UsersService`
The module registers `UserEntity` and exports its service.

**Rationale:** `WebhooksModule` imports `UsersModule` to inject `UsersService` — module isolation without re-exporting global services.
**Source:** 02.1-02-SUMMARY.md

## Lessons

### The pnpm `transformIgnorePatterns` allowlist had been a no-op for ~2 phases
The single regex `/node_modules/(?!(cuid2|...))` matched the *first* `/node_modules/` segment in pnpm's path `.pnpm/<pkg>/node_modules/<pkg>`; the text after it was `.pnpm/...` (not a package name), so the negative lookahead always passed and the ESM packages were never transformed. Earlier phases "fixed" the ESM error by adding packages to this allowlist — but the allowlist never actually matched pnpm paths until 02.1-02 diagnosed it.

**Context:** The real fix is a two-entry pattern: one pnpm-aware (`.pnpm/<pkg>/node_modules/<excluded>`) and one direct-layout (excluding `.pnpm`). A cosmetic config change that "looks right" can be inert under pnpm's store layout — verify the regex against an actual nested path.
**Source:** 02.1-02-SUMMARY.md, 02.1-01-SUMMARY.md

### `repository.upsert()` bypasses `@BeforeInsert`
The cuid2 id had to be pre-generated in the service because TypeORM's upsert path skips entity lifecycle hooks.

**Context:** Third member of the lifecycle-hook-bypass family — `repository.insert()` (Phase 5), `repository.upsert()` (here), `createQueryBuilder().insert()` (Phase 8). Any ORM bulk/insert shortcut skips `@BeforeInsert`; generate the PK explicitly.
**Source:** 02.1-02-SUMMARY.md

### `env.validation.spec.ts` broke again when a required var was added
Adding `WEBHOOK_SECRET` (and the earlier Auth0 vars) made the old spec fixtures throw, since they only supplied the original two vars.

**Context:** The same cross-file fixture break as Phase 2 — every time a required env field is added, the validation spec's full-config fixtures must be updated. Recurs because the fixture and the schema live apart.
**Source:** 02.1-04-SUMMARY.md

### `timingSafeEqual` throws on unequal byte lengths — pad, don't early-return
The TypeError is real, but the correct mitigation is padding to a common length, not returning early.

**Context:** A "defensive" early-return that avoids a crash can silently reintroduce a security hole (the length oracle). When working around a crypto-primitive constraint, check the workaround doesn't defeat the primitive's purpose.
**Source:** 02.1-REVIEW.md (CR-01), src/webhooks/guards/webhook-secret.guard.ts

### Jest 30 `--testPathPattern` → `--testPathPatterns`, and `pnpm test --` mis-routes it
`pnpm test -- --testPathPattern=...` passes the flag as a positional arg that never reaches Jest.

**Context:** Recurs across the whole project; invoke `pnpm jest --testPathPatterns=...` directly.
**Source:** 02.1-01-SUMMARY.md, 02.1-03-SUMMARY.md

## Patterns

### `@Public()` + route-level guard for an alternate auth scheme
Bypass the global JWT guard and enforce a different credential (shared header secret) on a single route.

**When to use:** Machine-to-machine callbacks (webhooks) that can't carry a user JWT but must still authenticate.
**Source:** 02.1-04-SUMMARY.md

### Feature-module isolation without APP_GUARD re-registration
Import the service-owning module, register only the route-specific guard; never re-add app-global guards.

**When to use:** Any feature module adding a route guard under a globally-guarded app.
**Source:** 02.1-04-SUMMARY.md

### Constant-time comparison with equal-length padding
Pad both inputs to `maxLen` zeroed buffers before `timingSafeEqual`.

**When to use:** Any secret/token comparison where inputs may differ in length — the canonical constant-time pattern.
**Source:** src/webhooks/guards/webhook-secret.guard.ts

### Two-entry `transformIgnorePatterns` for pnpm
One pattern for `.pnpm/<pkg>/node_modules/<excluded>`, one for direct `node_modules/<pkg>`.

**When to use:** Any Jest project on pnpm needing to transform ESM-only deps — the single-pattern form silently fails.
**Source:** 02.1-02-SUMMARY.md

### Wave 0 RED test stubs (TDD)
Specs import not-yet-existing modules to fail at import level before implementation.

**When to use:** Opening wave of every TDD phase — project-wide.
**Source:** 02.1-01-SUMMARY.md

### Layered defensive guard order
type-check → empty-check → constant-time compare, throwing 401 at each rejection.

**When to use:** Header-secret guards where absent, empty, and wrong-value inputs all need safe handling.
**Source:** src/webhooks/guards/webhook-secret.guard.ts, 02.1-03-SUMMARY.md

## Surprises

### The review-fix loop worked here — the opposite of Phase 1.1
A CRITICAL code-review finding (timing oracle) plus three warnings were all applied to the shipped code (verified in source: padded compare, 401, `@IsNotEmpty`, `@MinLength(32)`). Phase 1.1's equally-critical `synchronize` finding was ignored and cost two later phases; here the same review mechanism caught a security hole and it was actually closed.

**Impact:** Demonstrates the review process *can* prevent shipping a flaw — the differentiator is whether the finding gets an explicit adopt decision. Caveat: the planning artifacts (`02.1-03-SUMMARY.md`, STATE.md) were never updated and still describe the old early-return, so the written record understates the security posture of the code.
**Source:** 02.1-REVIEW.md, src/webhooks/guards/webhook-secret.guard.ts, 02.1-03-SUMMARY.md

### A config "fix" was inert for ~2 phases
The `transformIgnorePatterns` ESM allowlist that earlier phases kept appending to never actually matched pnpm's nested paths; the cuid2/jose ESM errors persisted (worked around by mocking) until 02.1-02 found the regex was matching the wrong `/node_modules/` segment.

**Impact:** Repeatedly editing a config that looks correct but is inert wastes effort and masks the real defect; a regex touching pnpm's store layout must be tested against a real `.pnpm/...` path, not assumed.
**Source:** 02.1-02-SUMMARY.md
